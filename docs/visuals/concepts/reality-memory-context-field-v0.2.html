先定义“上下文”是什么。

这里的上下文不是后端所有数据，也不是个人关系图。它是某个时间窗内，系统认为彼此相关、并可能对用户有价值的一组现实实体和状态。

活动片段例如出门、午餐、到家、洗衣、阅读。它可以成为短暂中心。
物品和空间钥匙、背包、胡辣汤、纸巾、玄关、厨房。它们因为片段而变亮。
状态变化位置移动、余量下降、被使用、归属确认、候选冲突。
语义关系偏好、任务、人际承诺、提醒策略。默认只展示强相关关系。

为什么不要以“我”为中心。

用户当然是数据的主人，但视觉上永远把“我”放中心，会让关系网像社交图谱或知识管理工具。Reality 更像现实中的天气图：今天哪个片段活跃，哪个片段就成为局部中心。

中心可以变化早上是出门，午间是午餐，晚上是到家或洗衣。用户不需要看到一个永久太阳系。
关系有生命周期强关系会变亮，过期关系会沉下去，长期有效的才进入稳定记忆。
不要显示全部默认只显示 5-9 个和当前片段有关的节点，其他记忆由 Agent 查询或深层页进入。
动效表达判断脉冲代表今天变化，虚线代表候选，实线代表确认，淡出代表不再活跃。

下一步建议

我建议正式 App 概念采用：光场 Agent 作为默认首页，上划或一句“看看今天”进入上下文场。对象详情再进入单物品时间轴。这样有灵气，也能解释记忆中台到底理解了什么。
