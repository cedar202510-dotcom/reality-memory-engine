# RV101 眼镜端与云端后端联调审查 v0.1

审查日期：2026-07-24  
眼镜端基线：`main` 分支 `apps/reality-memory-glasses/`  
后端基线：`origin/backend` 分支 `e1c0fe6`  
结论状态：尚不能直接联调，核心记忆链路已具备一部分实现

## 1. 结论

当前不是“眼镜 APK 加后端就已经形成完整产品闭环”。

两边在核心原则上基本一致：采集端只产生证据；模型只产生原子观察和记忆候选；
只有候选门可以追加 `MemoryEvent`（记忆事实事件）；`StateProjection`（当前状态）
可以从事件流重算。

但实际代码之间还没有可用的上传通道，字段契约和媒体处理也没有对齐。即使现在把
后端地址写进 APK，请求也会因为设备标识、模态枚举和加密格式不兼容而失败。
后端目前真正跑通的是“已收到可读图片或音频之后”的部分流程，不是从眼镜到提醒
投递的完整流程。

## 3. 不能直接通信的阻断项

### 3.1 没有眼镜上传器

眼镜端只把密文和 JSON 放入本地 Outbox（待上传队列），没有 HTTP 客户端、设备注册、
鉴权、断点重试、服务端确认和删除回执。后端也没有实现正式契约已经定义的
`evidence/init -> 上传密文 -> complete -> delete-receipt` 四段接口。

### 3.2 SourceEnvelope 契约不是同一个版本

眼镜端遵循仓库正式的 `rme.source-envelope.v1`，后端入口使用一份为早期 iOS 探针
缩减的 `SourceEnvelopeIn`。

| 字段 | 眼镜端 | 后端入口 | 结果 |
| --- | --- | --- | --- |
| `device_id` | `glass_<UUID>` 稳定匿名标识 | PostgreSQL 设备表 UUID | 422 校验失败 |
| `modality` | `IMAGE` / `VIDEO` / `AUDIO` / `SENSOR` | 小写枚举 | 422 校验失败 |
| 会话和窗口 | 三个独立 ID | 只有 `source_session_id` | 多模态关系会丢失 |
| 双时间标尺 | UTC + 单调时钟 + 误差 | 只接收两个 UTC 时间 | 精确对齐信息会丢失 |
| 采集原因 | `CaptureIntent.signal_kind` | `explicit/auto/ring_motion` | 眼镜头动原因无法无损表达 |
| 策略与设备能力 | 正式字段 | 只能临时塞入 `meta` | 无冻结校验 |

不应让眼镜端退回早期 iOS 缩减契约。正确做法是让后端接入层接受正式 v1 契约，
再映射到内部数据库模型。

### 3.3 媒体加密方式不兼容

眼镜端当前 Outbox 是 Android Keystore 的 AES-256-GCM 密文。后端入口把上传字节
直接交给图片哈希、图片解码或 ASR，无法读取这种密文；而且设备级 Keystore 密钥
不能从眼镜导出。

正式联调需要实现正式契约中的“每项证据数据密钥 + 服务端可解封装密钥”方案，
或先做严格限定的 Debug 联调适配器。不能把生产方案改成长期上传明文。

### 3.4 视频和传感器只是枚举存在

后端入口把所有非音频证据都投递到 `frame.process`。因此：

- `video` 会被当成图片计算感知哈希并交给图片模型，不能正常处理；
- `sensor` 会被当成图片处理，不能正常处理；
- 目前只有 `image` 和 `audio` 有对应解析器；
- 原始 PCM 还需要明确采样率、通道和编码，最好上传 WAV 或让 ASR 接口接收完整
  音频格式元数据。

### 3.5 中间语义层只有文档，没有代码

架构中的 `ObservationBundle`（同一变化的观察包）和 `ActivityEpisode`
（一段可修订的现实活动，例如用餐）在后端文档中有定义，但数据库模型和处理器中
没有实现。当前图片或音频观察会直接生成单条记忆候选，尚不能可靠处理：

- 同一窗口内“看到外卖 + 听到用户说不好吃”的跨模态关联；
- 多张近似图片的代表证据选择和语义增量判断；
- 一段用餐、阅读或找物活动的开始、延续和结束；
- 多条弱观察合并后再提高或降低置信度。

### 3.6 Agent 只完成了查询和解析辅助

代码中的 Agent 目前是受约束的阶段模型：图片描述、观察抽取、语音语义抽取和找物
回答。它不是完整的产品“顾问”。

`MemorySignal`（值得关注的状态信号）、`ReminderDecision`（是否以及何时提醒）、
`ReminderDelivery`（投递、查看、忽略）目前只有架构文档，没有 API、数据库表、
订阅队列或眼镜下行通道。因此眼镜 UI 能展示本地测试提醒，但还收不到云端 Agent
的真实提醒。

### 3.7 生产边界尚未具备

后端当前是单家庭 seed 数据，没有用户鉴权、设备绑定、家庭域隔离和设备令牌。
Outbox worker 单条失败后直接标记已消费，没有重试和失败队列。它适合开发验证，
不适合接收真实用户持续数据。

## 4. 推荐的最小联调顺序

### 第一步：只打通图片和音频上传

1. 后端实现正式 v1 的设备注册与证据四段上传接口。
2. 眼镜端实现网络检测、上传状态机、幂等重试和服务端确认。
3. 图片保持 JPEG；音频从裸 PCM 封装为带格式头的 WAV，保留真实通道、采样率和时长。
4. 服务端接收密文和封装的数据密钥，解密后的临时媒体才进入现有图片/音频解析器。
5. 保留 `capture_window_id`、三个时间字段和采集原因，验证同窗图片与音频能共同查询。

这一步不接视频、传感器解析，也不做提醒下行，先证明：

```text
眼镜采集
  -> 安全上传
  -> 图片/音频原子观察
  -> 记忆候选
  -> 记忆事实事件
  -> 当前状态与查询
```

### 第二步：补观察组合和活动段

按 `capture_window_id` 和时间范围生成 `ObservationBundle`，实现重复图片筛选、图片与
音频联合解释，再实现可修订的 `ActivityEpisode`。这一步完成后，类似“画面中正在
吃某份外卖，同时用户说这个胡辣汤不好喝”的信息才有合理的结构化落点。

### 第三步：实现顾问信号和眼镜提醒下行

先实现任务和耗材两类受控信号，再加入冷却、去重、过期、用户当前状态和投递审计。
眼镜端只接收结构化提醒载荷并显示或播报，不允许 Agent 直接改写事实，也不执行
购物、发消息等外部动作。

## 5. 本轮明确不做

- 不把 `ActivityEpisode` 放到眼镜端判断；
- 不把头动阈值命中解释成用户具体行为；
- 不为迁就后端早期接口而删除正式 v1 的窗口和双时间字段；
- 不把 Debug 明文媒体方案当成生产上传方案；
- 不宣称视频、传感器、主动提醒已经端到端跑通。
