# RV101 真机数据与电脑后端联调审查 v0.2

审查日期：2026-07-24

真机数据：`origin/glasses-debugdata`，提交 `b91a0c1`

眼镜运行时：`android-glasses/0.1.0`

后端基线：`origin/backend`，提交 `e1c0fe6`

## 1. 真机数据实际包含什么

这不是模拟数据，而是 RV101 上
`/data/data/com.realitymemory.glasses/files/reality-memory/` 的应用私有目录导出。

有效会话中共有 7 个采集窗口：

- 5 段约 9.984 秒的 16 kHz、8 通道 PCM 音频；
- 6 段眼镜原生加速度计和陀螺仪窗口；
- 5 次头动自动触发，其中 3 次被判定为强变化、2 次为中等变化；
- 4 次图片请求和 3 次短视频请求全部失败；
- 11 项成功证据均生成了来源信封、证据项、采集尝试、密文和 Debug 明文副本。

传感器每段为 369 至 435 个样本，实际采样率稳定在约 50.57 Hz，样本间隔约
19.78 ms。说明 RV101 原生六轴读取、触发器、前后窗缓存和 NDJSON 落盘已经工作。

音频每段明文为 2,555,904 字节，即 159,744 个八通道采样帧，对应 9.984 秒。
说明 Rokid 8 通道 `AudioRecord` 路径确实初始化成功，没有走单声道降级。

## 2. 数据暴露出的采集端问题

### 2.1 相机尚未成功

所有图片和视频尝试都是 `DEVICE_UNAVAILABLE`，延迟为 0 ms。这表示 CameraX 在
服务启动阶段就没有准备成功，并不是运动没有触发相机。旧版本没有把 CameraX
初始化异常和相机清单写入导出数据，所以仅凭本包无法判断是：

- 固件没有把世界相机暴露给 Camera2；
- `DEFAULT_BACK_CAMERA` 的镜头方向声明不符合 RV101；
- 同时绑定 `ImageCapture + VideoCapture` 的用例组合不受支持；
- 生命周期、权限或厂商相机占用导致绑定失败。

联调版已增加相机清单和完整错误审计，并在图片与视频组合绑定失败时降级为只绑定
图片。下一轮导出中应出现 `CAMERA_PREPARED`、`CAMERA_PREPARED_IMAGE_ONLY` 或
`CAMERA_PREPARE_FAILED`。

### 2.2 来源信封的时间范围不准确

传感器文件包含触发前缓存，但旧版本来源信封的 `monotonic_start_ns` 写的是动作
触发时刻。六个样本窗口中，实际文件起点分别比信封起点早约 1.17 至 4.00 秒。

这会让后端错误理解图片、语音和动作的先后关系。联调版改为：

- 传感器来源信封使用第一条和最后一条真实样本时间；
- 音频使用 `AudioRecord` 真正开始和结束的单调时间；
- 图片和视频使用相机请求到完成的实际单调时间；
- `CaptureIntent` 仍只表达触发动作本身；
- `CaptureWindow` 仍表达这一批多模态采集的总窗口。

因此三者不能互相替代：采集意图是“为什么触发”，采集窗口是“哪些证据属于同一批”，
来源信封是“这一项证据实际覆盖哪段时间”。

### 2.3 证据摘要记录成了密文摘要

旧版本 `EvidenceItem.byte_count` 和 `sha256` 来自 AES-GCM 密文。每个密文比明文多
16 字节，而且随机 IV 会让同一明文每次产生不同摘要。后端无法用它校验上传明文，
也不能稳定去重。

联调版改为：

- `EvidenceItem.byte_count` 和 `sha256` 描述原始证据明文；
- `extensions.ciphertext_byte_count` 和 `ciphertext_sha256` 描述本地传输对象；
- 加密算法、密钥引用和 IV 仍保留在 `encryption`。

### 2.4 音频已录到，但尚不能证明有人声质量

五段音频八个通道都有可解析的 PCM 帧；四个原始麦克风通道通常有信号。但本批峰值
整体较低，且没有测试者同步标注“哪一秒说了什么”，因此只能证明音频链路工作，
不能证明真实 ASR 可用或语音内容清晰。

联调版后端保留原始八通道证据，同时在送入 ASR 前把 `RAW_MIC_0..3` 临时混成单声道
WAV。该 WAV 只用于解析，不替换原始证据。

### 2.5 轴向仍未校准

采样率和数值连续性已经确认，但 `x/y/z` 在 RV101 上分别对应头部哪个方向仍为
`UNVERIFIED_RV101`。现有触发器只使用向量幅值和积分旋转，暂不依赖精确轴向；
未来要判断抬头、低头、左转或右转时必须做重复标注采样。

## 3. 与最新后端原有实现的未对齐

| 项目 | 眼镜正式契约 | 后端原入口 | 本轮处理 |
| --- | --- | --- | --- |
| 来源信封 | 完整 `rme.source-envelope.v1` | 早期 iOS 缩减结构 | 新增 `/internal/v1/device-evidence` |
| 设备编号 | `glass_<UUID>` | PostgreSQL UUID 外键 | Debug 入口保留原编号，内部设备绑定后续补 |
| 模态 | 大写正式枚举 | 小写内部枚举 | 接入层转换，不修改端侧契约 |
| 会话关系 | Session、Intent、Window 三层 | 只有 source session | 原始契约完整保存在接入元数据 |
| 双时间标尺 | UTC + 单调时钟 + 误差 | 只有 UTC | 完整接收并保留 |
| 视频、传感器 | 可采集证据 | 被误投图片解析器 | 只可靠落盘，暂不解析 |
| 8 通道 PCM | 裸 PCM + 完整媒体参数 | ASR 只收到无格式字节 | 解析前临时转单声道 WAV |
| 本地加密 | Android Keystore AES-GCM | 服务端无法解密 | Debug 仅受控明文；生产密钥封装仍待实现 |

## 4. 当前可以跑通的范围

使用开发线和 `adb reverse` 后，可以跑通：

```text
RV101 Debug APK
  -> 生成正式来源信封、证据项和明文 Debug 副本
  -> HTTP 自动重试上传
  -> 开发线端口反向映射
  -> 电脑 FastAPI 后端
  -> 图片/音频进入现有解析队列
  -> 视频/传感器可靠保存但暂不做语义解析
```

这属于设备联调闭环，不是生产安全闭环。生产仍需要设备绑定、鉴权、每项证据数据
密钥、服务端可解封装密钥、上传确认、端侧删除和删除回执。

## 5. 下一轮真机必须保留的结果

1. 完整 `collect-test-results.sh` 结果包，不只导出应用数据。
2. `logcat.txt`、`device-getprop.txt`、`package-after.txt` 和相机审计事件。
3. 至少一次明确口播及其开始时间，例如“现在开始语音测试，我不喜欢这碗胡辣汤”。
4. 静坐、左右转头、抬头、低头、起身和行走各重复 3 次，并记录动作顺序。
5. `*.upload.json` 与后端审计响应，确认断线后能够重试且同一证据只入库一次。
6. 若相机仍失败，必须保留 `CAMERA_PREPARE_FAILED` 的完整错误与相机清单。
