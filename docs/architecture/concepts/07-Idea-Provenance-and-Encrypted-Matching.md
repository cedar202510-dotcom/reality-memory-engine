## 0. 先说结论

需求是三件事，它们的可行性差异极大：

| 需求 | 判断 | 说明 |
|---|---|---|
| **P1 证明我在某时刻持有某 idea** | ✅ 已解决的问题 | 加盐哈希 + 时间戳锚定。技术成熟、成本近零，可以现在就做 |
| **P2 内容对平台和他人保密** | ✅ 可解决 | 本地加密 + 只上传承诺。工程直接 |
| **P3 在保密状态下被相似需求方发现** | ⚠️ **根本受限** | 不是工程难度问题，是信息论限制。见 §4 |
| **P4 撮合后完成可信交易** | ⚠️ 部分可解决 | commit-reveal 解决「一致性验证」，**不解决「估值」**。见 §8 |

**核心判断：真正的障碍不是密码学，是 Arrow 信息悖论和双边市场冷启动。**
把工程重点放在密码学上，会解决一个不是瓶颈的问题。

本文档因此分两部分：§1-§7 是机制设计（怎么做对），§8-§10 是可行性判断（该不该做、什么时候做）。

## 1. 需求重述与三者的内在冲突

用户的原始判断值得先记录下来，因为它是对的：

> 当下社会 idea 是廉价的，但随着 AI 让落地成本不断降低，idea 变得越来越重要，
> 之后可能成为可以交易的东西，但现在又没有什么机制去保护 idea，没法解决信任问题。

并且特别指出：**很多时候提出问题才是最关键的**。这一点在 §6 单独处理，因为
「问题」在密码学上和法律上都比「方案」更脆弱。

三个需求的冲突结构：

```
        P1 证明持有
        （需要发布承诺）
              │
              │  兼容
              ▼
        P2 内容保密  ◄──── 直接对立 ────►  P3 可被发现
        （不能泄漏）                      （必须泄漏一些）
```

- **P1 与 P2 兼容**：哈希是单向的，发布哈希不泄漏内容。这条路没有矛盾。
- **P2 与 P3 直接对立**：要让别人找到你，系统必须能对内容做某种判断；
  能判断就能被用作探测。这不是实现问题，见 §4。

**「价值来自稀缺，证明来自公开」这句话只对了一半。** 更准确的表述是：
证明可以不公开（哈希就够了），但**发现必须泄漏**。矛盾在 P3，不在 P1。

## 2. 威胁模型

不写清楚防谁，后面所有机制都无法评价。

| 编号 | 对手 | 能力 | 目标 |
|---|---|---|---|
| **A1** | 平台运营方 | 读全部数据库、日志、网络流量；可修改服务端代码 | 挖掘 idea 库自用或转卖 |
| **A2** | 其他用户 | 可无限次提交 idea 并观察匹配结果 | 探测他人 idea 内容（探针攻击） |
| **A3** | 链上观察者 | 读全部历史链数据，永久且不可撤回 | 从链上数据反推内容或行为模式 |
| **A4** | 交易对手 | 谈判中合法获得部分或全部内容 | 拿到内容后终止交易、自行实施 |
| **A5** | 事后争议第三方 | 法院 / 仲裁 / 专利审查 | （非对手）需要被说服的验证方 |
| **A6** | 模型服务商 | 若 embedding / LLM 调用走外部 API，可见明文 | 训练数据获取 |

**A1 和 A6 决定了一条硬约束**：只要 idea 明文或 embedding 经过服务端，
「平台看不到」就是空话。所以 [06 号文档 §11-Q5](../06-Idea-Capture-Sidecar-Architecture.md)
把「服务端是否存 embedding」列为待决问题——它不是性能选择，是威胁模型的分水岭。

**A2 是最容易被忽略、也最难防的**，见 §4。

## 3. 分层机制

```
L0  本地明文             用户设备 / 自托管，不出信任域
     │
L1  承诺层               salted hash，本地计算，可发布
     │
L2  锚定层               每日 Merkle root → 时间戳（可选上链）
     │
L3  发现层               ★ 难点：如何在保密下被匹配（§4、§5）
     │
L4  谈判与结算层         commit-reveal + 托管 + 分账（§7）
```

### 3.1 L1 承诺层

对每条 `idea_record` 计算：

```
salt        ← 32 字节 CSPRNG，每条独立
canonical   ← 确定性序列化(kind, title, body, created_at, actor_pubkey)
commitment  ← SHA-256(canonical ‖ salt)
```

三个设计要点：

1. **salt 必须有，且必须高熵。** idea 文本的信息熵很低——一个问题可能只有 20-50 个
   token，且高度符合语言模式。无盐哈希面对字典/枚举攻击几乎等于明文。
   这一点对「问题」尤其致命，见 §6。
2. **canonical 序列化必须确定性。** 字段顺序、Unicode 规范化（NFC）、时间格式、
   数字表示都要固定，否则同一内容在不同版本算出不同 hash，整个存在性证明直接失效。
   建议直接采用 JCS（RFC 8785）而不是自造规则。
3. **承诺里绑定作者公钥。** 否则承诺可被任何人复制转发——A 公开 commitment 后，
   B 可以原样再发一次，两人的承诺无法区分先后归属。

> `salt` 存哪里是关键：它必须与内容一起保存在用户信任域内。
> **salt 丢失 = 永远无法揭示 = 承诺变成废数据。** 需要纳入备份与恢复流程。

### 3.2 L2 锚定层

单条 commitment 逐条上链在成本和隐私上都不合理（每条一笔交易，且交易时间模式泄漏行为）。
标准做法是批量：

```
每天收集当日全部 commitment
  → 排序 → 构建 Merkle 树 → 得到 daily_root
  → 只发布 daily_root（一天一笔）
  → 为每条 commitment 保存 Merkle inclusion proof（本地）
```

事后要证明某条 idea 的存在时间：出示 `内容 + salt + inclusion proof + daily_root 的锚定记录`。
验证方重算即可，不需要信任任何人。

优点：
- 成本与 idea 数量无关，每天一笔
- 链上只有一个 32 字节随机串，**不泄漏当天有几条 idea、也不泄漏任何内容**
- 锚定目标可替换（比特币 / Injective / 甚至传统可信时间戳机构），不锁定

### 3.3 L3 / L4

见 §4-§7。

## 4. P3 的根本限制：匹配即预言机

这是整份文档最重要的一节。

**命题**：任何能够回答「A 的 idea 与 B 的 idea 是否相似」的系统，
都可以被用作逼近内容的预言机。

**攻击**（对手 A2）：
1. 攻击者构造探针 idea `p₁`，提交，观察是否与目标匹配
2. 根据结果调整探针语义方向，提交 `p₂`
3. 重复——这是对语义空间的二分搜索

若相似度阈值输出是布尔值，每次查询泄漏约 1 bit；若输出连续相似度分数，
每次泄漏远多于 1 bit，逼近速度快一个量级。

**这个限制无法用密码学消除。** 同态加密、MPC、TEE 保证的是「除了约定输出之外什么都不泄漏」，
但**约定输出本身就依赖内容**。密码学能做的是把泄漏量收敛到「仅输出」，
不能让输出为零——输出为零的系统不能匹配任何东西。

### 4.1 因此防御必须是经济学的

唯一可行的防线是让探测的**成本 × 次数 > idea 的价值**：

| 手段 | 说明 |
|---|---|
| 查询需质押 / 付费 | 每次匹配请求消耗真实成本，探针攻击的边际成本不为零 |
| 查询者实名 / 可审计 | 匿名无限刷是攻击的前提条件，去掉匿名性代价陡增 |
| 速率限制 + 异常检测 | 同一账户高频语义邻近提交是明显的攻击特征 |
| 只输出布尔，不输出分数 | 把单次泄漏压到 1 bit 上限 |
| 匹配结果需**双方同意**才揭示对方存在 | 单方无法确认「有人和我相似」，探针拿不到稳定信号 |
| 承诺先行 | 提交探针也必须先做 L1 承诺，攻击者被迫留下自己的时间戳记录 |

最后两条最有价值：**双向同意**把预言机从「查询即得答案」变成「查询需对方配合」，
探针攻击的成功率直接依赖被攻击者的行为，而不只是攻击者的算力。

### 4.2 诚实结论

> 一个「完全保密又能被自动发现」的 idea 市场在信息论上不存在。
> 可以做到的是「泄漏量可控、探测成本高于收益」的市场。
> 任何声称做到前者的方案，要么定义了不同的问题，要么在骗人。

## 5. L3 发现层的候选机制

> **本节的工程成熟度判断待补**（调研进行中）。以下先记录机制结构与各自的
> 泄漏面，性能数字与库选型在 v0.2 补入。

### 5.1 方案 E：公开抽象层（无密码学）

**用户自己写一段可公开的需求描述（teaser），核心方案保密。**

这是现实世界 IP 市场（技术转移、专利经纪、VC pitch、猎头）实际运行的方式。
被严重低估，因为它不酷。但它有三个密码学方案给不了的优点：

1. **脱敏边界由用户判断**——用户最清楚哪部分能说、哪部分是核心。
   任何自动化机制都在替用户做这个判断，且做不好。
2. **零实现成本**，零新增信任假设。
3. **teaser 本身可以被搜索、被人工浏览、被推荐**，冷启动阶段唯一可行的匹配方式。

缺点：teaser 写得太抽象就匹配不到，写得太具体就泄漏。这个权衡无法消除，
但它被移交给了唯一有资格做这个权衡的人。

### 5.2 方案 A：语义 LSH 分桶 + OPRF 盲化

```
本地：text → embedding → LSH → bucket_id
     → OPRF(bucket_id) 与独立密钥持有方交互 → blinded_bucket
上传：仅 blinded_bucket（伪随机串，平台只能判等，不能反推语义）
匹配：落入同一 blinded_bucket 的用户互为候选
```

关键约束：
- **OPRF 密钥不能由平台持有**，否则平台可自行枚举字典把 bucket 映射回语义。
  需要独立方或阈值分片持有 + 严格速率限制。
- **原始 embedding 绝不能上传**——见 §5.5。
- bucket 粒度决定召回/泄漏权衡，粗则匹配噪声大，细则泄漏多。

### 5.3 方案 B：概念标签集合 PSI

把 idea 拆成概念标签集合，对标签做 OPRF-based PSI，求交集大小。
标签空间小意味着字典攻击风险高，OPRF 是必需的而非可选的。

### 5.4 方案 C：同态加密向量内积

CKKS 类方案可以在密文上算余弦相似度。全库 N×N 比对不现实，
标准结构是两阶段：LSH 粗筛出候选集 → 候选对之间 HE/MPC 精算，只输出「是否 ≥ 阈值」。

关键问题是**谁持有解密密钥**——若平台持有则整套机制失去意义，需要阈值解密或
把比较步骤放进两方 MPC。

### 5.5 embedding 反演：一条硬约束

文本 embedding **可以被反演回接近原文的文本**（Vec2Text 一系工作）。
短文本（正是「一个问题」的长度）反演成功率尤其高。

**结论：原始 embedding 必须被视为等同于明文。**
把它上传给不可信平台，等于放弃 P2。这直接决定了：

- [06 号文档](../06-Idea-Capture-Sidecar-Architecture.md) 的 `idea_records.embedding`
  字段，在接入任何撮合机制之前，**只能存在于用户信任域**
- 若要做服务端向量检索，必须先解决「服务端持有向量」这一前提，
  而不是把它当成实现细节

> 具体反演成功率、防御手段有效性、以及各方案的性能数字与可用库状态，
> 调研完成后补入 v0.2。

### 5.6 方案 D：TEE

工程上最省事：在飞地内做明文比对，用 remote attestation 证明运行的是审计过的代码。
代价是信任从密码学假设转移到硬件厂商与侧信道假设。作为过渡方案合理，
作为长期承诺不合理——尤其不能对用户宣称「我们看不到」。

## 6. 「保护问题」为什么更难

用户特别指出问题往往比答案更关键。这个判断是对的，而且**问题在每一层都更脆弱**：

| 维度 | 方案 / 答案 | 问题 |
|---|---|---|
| 文本长度 | 长，熵高 | **短，熵低** → 字典枚举可行 → 加盐是强制的 |
| 价值转移 | 需要理解全部细节才能复制 | **知道问题指向哪，价值就转移了大半** |
| 匹配泄漏 | 匹配只说明方向接近 | 匹配几乎等于确认问题本身 |
| 著作权 | 表达可受保护 | **思想不受保护，问题几乎必然是「思想」** |
| 专利 | 可能满足新颖性 | 问题本身通常不是可专利客体 |
| 商业秘密 | 可以 | **可以——但这是唯一路径** |

### 6.1 由此得出一个真实的法律用途

既然商业秘密是问题的唯一保护路径，而商业秘密的构成要件之一是
**「权利人采取了相应保密措施」**，那么：

> 时间戳锚定的真实价值不是「确权」，而是佐证
> **「在特定时点已持有该信息，且已采取保密措施」**。

这比「上链确权」的说法务实得多，也是链在这个场景里唯一站得住的法律叙事。
承诺记录 + 加密存储 + 访问审计，三者合起来构成一组可举证的保密措施证据。

> 各法域对链上时间戳证据效力的实际认定情况，调研后补入 v0.2。

### 6.2 机制上的推论

- 问题类条目（`kind=QUESTION`）默认**不进入自动匹配池**，必须用户逐条显式开启
- 问题的 teaser 应鼓励写成「领域 + 约束」而非「问题本身」
- 问题的匹配阈值应显著高于方案，宁可漏配

## 7. L4 谈判与结算

### 7.1 commit-reveal 解决的和不解决的

**解决**：谈判中的一致性验证死锁。
「我不告诉你内容你不给钱，我告诉你了你就不给钱」——

```
1. 卖方早已发布 commitment（L1/L2）
2. 双方签订链上托管：买方锁定资金，约定揭示期限
3. 卖方向买方揭示 (内容, salt)
4. 买方本地验证 SHA-256(canonical‖salt) == commitment
   → 确认「这确实是你当初承诺的那个东西，不是临时编的」
5. 托管释放 / 或买方在争议期内提出异议进入仲裁
```

**不解决**：估值。见 §8。买方验证了「内容与承诺一致」，但这不告诉他内容值不值钱。

### 7.2 链在这里的角色（不多不少三件事）

1. **时间戳锚定**：daily Merkle root
2. **托管与结算**：escrow、分期揭示、争议期、可选的后续分成
3. **争议证据**：不可篡改的时间线

### 7.3 链明确不做

| 不做 | 原因 |
|---|---|
| 存 idea 内容（哪怕加密） | 链上数据永久且不可撤回，密钥泄漏或算法老化 = 永久泄漏。与 GDPR/个人信息保护的删除权直接冲突 |
| 做相似性检索 | 检索完全不需要链；放链上只会把泄漏永久化 |
| 判定「谁原创」 | 哈希证明的是「谁先发布哈希」，不是「谁先想到」。哈希别人的 idea 一样能发 |
| 把 idea 做成可交易 token | 可能构成证券，监管风险与产品收益不成比例 |

### 7.4 关于 Injective agent-skills

[InjectiveLabs/agent-skills](https://github.com/InjectiveLabs/agent-skills) 是
**给 Agent 使用 Injective 链的技能包**：CLI 与钱包管理、代币元数据与转账、
行情与预言机数据、质押、跨链桥、EVM 合约开发、前端签名（Keplr/MetaMask/CosmJS）、
AuthZ 会话委托自动签名等。

它是**工具层，不是方案层**。它能让 agent 方便地部署合约、发起交易；
但 §3.2 的锚定合约、§7.1 的托管与揭示合约，逻辑都要自己写。可对应的落点：

| 本文档需要 | agent-skills 中对应 |
|---|---|
| 锚定合约、托管合约 | `injective-evm-developer` |
| 用户侧签名 | `injective-frontend-wallet` |
| 运维与查询 | `injective-cli` |
| 自动化结算（谨慎） | `injective-trading-autosign` |

**一个必须写下来的反对意见**：引入加密货币基础设施，会给一个以家庭隐私与
信任为核心卖点的产品带来钱包管理、助记词、税务、监管和「这是不是个币圈项目」的
认知负担。方向与 Reality Memory 的信任叙事相反。

> **建议：若真要做，做成独立产品线、独立 App、独立品牌**，
> 与 Reality Memory 主体只共享灵感捕捉的数据导出接口，不共享账号体系与信任叙事。

## 8. 真正的障碍：Arrow 信息悖论

用户描述的困境有名字，而且比区块链早 60 年。

Kenneth Arrow 在 1962 年指出：**信息商品的价值，买方在购买前无法评估；
一旦评估了（即知道了内容），就不再需要购买。**

这是信息经济学的经典结论，不是工程缺陷。commit-reveal 解决的是
「揭示后能否验证一致性」——这是**诚信问题**；Arrow 悖论是
「揭示前能否定价」——这是**估值问题**。两者不同，后者才是市场做不起来的主因。

社会对这个悖论已有的部分解法，全都不是密码学：

| 解法 | 机制 | 对本设计的启发 |
|---|---|---|
| 专利制度 | 强制公开换取有限期垄断 | 公开是特性不是 bug；「保密交易」逆着制度设计走 |
| NDA + 分阶段披露 | 法律责任替代技术保证 | 分阶段披露值得直接借鉴（§8.1） |
| 声誉中介 | 经纪人/VC 承担评估成本 | 中介的价值在**筛选**，不在保密 |
| 期权化定价 | 先小额付费看部分，满意再付全款 | 与 escrow 天然兼容，是最可落地的一条 |
| 雇佣而非购买 | 直接买人不买 idea | 市场事实上的主流解 |

### 8.1 因此 L4 应该是分阶段的

不要设计成「一次付款换一次揭示」，而是：

```
阶段 1  公开 teaser                        免费
阶段 2  小额付费 → 揭示问题的完整表述        买方获得评估所需的最小信息
阶段 3  签署条款 → 揭示方案细节              托管 + 争议期
阶段 4  落地后分成（可选）                   链上分账
```

每一阶段的揭示量与付费额都递增，买方逐步获得估值能力，卖方逐步获得补偿。
这是对 Arrow 悖论**唯一有实际战绩的应对**，且它是市场设计而不是密码学。

## 9. 什么会杀死这个想法

按杀伤力排序，密码学问题排在最后：

1. **双边市场冷启动。** 没有买方就没有卖方。这与本文档全部技术内容无关，
   却是最可能的死因。
2. **Arrow 悖论（§8）。** 结构性障碍，只能缓解不能消除。
3. **「idea 廉价、执行稀缺」可能仍然成立。** 用户的前提是「AI 降低落地成本 →
   idea 变贵」。这个推论有一个反向可能：若落地成本趋近于零，
   **验证一个 idea 好坏的最便宜方式就是直接做出来**，而不是购买。
   AI 可能同时降低「实施成本」和「idea 的稀缺性」（AI 也能生成 idea）。
   **这个前提是否成立，应该先用 Phase 2 的小规模市场去验证，而不是先建基础设施。**
4. **监管。** idea token 的证券属性、跨境数据、支付合规。
5. **法律保护薄弱。** 思想不受著作权保护，问题通常不可专利，商业秘密要求持续保密措施。
6. **密码学工程难度。** 真实存在，但排第六。

## 10. 分阶段路线与建议

| Phase | 内容 | 依赖 | 建议 |
|---|---|---|---|
| **0** | `content_hash` + `hash_salt` + canonical 序列化（JCS），本地保存，不上链、不做市场 | 仅 [06 号文档](../06-Idea-Capture-Sidecar-Architecture.md) | ✅ **建议做**。几十行代码，零外部依赖，保留一切未来选项 |
| **1** | daily Merkle root + inclusion proof + 锚定到**免费的公共时间戳服务** | Phase 0 | ⏸ 可做。仍不引入加密货币依赖 |
| **2** | teaser 公开撮合（§5.1 方案 E），人工或半自动匹配，小范围验证 | Phase 1 | ⏸ **这是真正的验证点**：先证明有人想交易 |
| **3** | 密码学发现层（§5.2-5.4）+ 链上托管结算 | Phase 2 **必须先成功** | ❌ 现在不做 |

### 10.1 明确的建议

**现在只做 Phase 0。**

理由：

- 灵感能否被稳定捕捉都还没验证（[06 号文档 §12](../06-Idea-Capture-Sidecar-Architecture.md) 的验收标准一条都还没跑通）。
  捕捉率、转写质量、误触率是真问题；确权是想象出来的问题。
- Phase 0 的成本极低（canonical JSON + 加盐 SHA-256），
  却保留了 Phase 1-3 的全部可能性——哈希算法和 salt 一旦定下来，
  未来任何时候都能补锚定。**反过来则不成立**：现在不留哈希，将来所有历史 idea 都无法追溯证明。
- 项目里已有同构先例可以照抄：
  [`DeletionTombstone.audit_hash`](../../../services/memory-platform/app/models/__init__.py:544)
  就是「证明删过、内容不可逆」。这里是「证明想过」，同一套路。

### 10.2 Phase 0 验收

1. 同一内容在不同机器、不同版本上算出相同 `content_hash`（canonical 序列化的确定性）
2. `salt` 进入备份与恢复流程，丢失场景有明确提示
3. 有一个离线校验脚本：输入 `内容 + salt`，输出 hash，可被第三方独立运行
4. 文档写清楚：**这不是法律确权**，是持有时点的技术证据

## 11. 待决问题

- **Q1** `content_hash` 是否绑定作者公钥？绑定需要用户密钥体系（当前没有），
  不绑定则承诺可被复制转发。倾向绑定，但要先有密钥管理方案。
- **Q2** canonical 序列化直接用 JCS（RFC 8785）还是自定义？倾向 JCS，避免自造规则。
- **Q3** Phase 1 锚定目标：比特币（最强不可篡改性，但确认慢）、Injective（快、便宜，
  但生态绑定）、还是传统可信时间戳服务（法律认可度可能更高）？
- **Q4** 若做 Phase 2，teaser 市场是否应完全脱离 Reality Memory 账号体系？
  倾向是（见 §7.4）。
- **Q5** §9-3 的前提（AI 是否真的让 idea 变贵）需要独立验证。
  建议作为一次小规模用户访谈的主题，而不是当作已成立的假设去建系统。
