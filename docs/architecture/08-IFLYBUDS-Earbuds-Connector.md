# IFLYBUDS 耳机接入 Connector

> 文档版本：v0.1
> 更新日期：2026-07-25
> 负责范围：科大讯飞 IFLYBUDS Air 2（及同类蓝牙 TWS 耳机）如何接入 Reality Memory，
> 提供音频输入与音频推送两个方向
> 上游文档：[04 设备接入 Connector 架构](04-Device-Connector-Architecture.md)、
> [05 设备与云端通信](05-Device-Cloud-Communication.md)
> 实现：[`apps/iflybuds-collector/`](../../apps/iflybuds-collector/)

## 1. 结论

能接，但**耳机不是 connector 的对端**。

04 号文档里 `services/memory-platform/app/connectors/` 那一层是**下行控制通道**，它的
前提是设备上跑着一个能收命令的我方 runtime（adb 发 intent、inbox 等设备来拉）。TWS 耳机
是 A2DP/HFP 从设备加厂商 App，跑不了我方代码，也不会来拉 inbox——给它写一个
`IflybudsConnector` 没有意义，对端没有东西接收 `CAPTURE_REQUEST`。

所以三段式里的「设备侧 Collector」落在**宿主机**上，耳机只提供麦克风和扬声器：

```text
[设备侧 Collector]                    [传输契约]              [平台侧 Adapter]
IFLYBUDS Air 2 (HFP mic / A2DP out)
  ↓ CoreAudio
宿主机采集器（Mac，未来可换手机 App）  ->  SourceEnvelope   ->  Ingest API
  ↑ inbox / WS 订阅下行                   + DeliveryReceipt      device_messages
```

代价与收益都很明确：多了一台必须在场的宿主机，换来的是**后端一条新链路都不用加**。
控制通道复用现成的 `inbox`，`CONTROL_TRANSPORTS` 不变，采集动作 `CAPTURE_AUDIO` 不变，
提醒消息 `REMINDER_SIGNAL` 不变。后端为这副耳机新增的全部代码是一个设备注册端点，
而那个端点本来就是 04 §5.5 第 4 步要求的，不是为耳机特设的。

## 2. 设备身份

| 字段 | 取值 |
| --- | --- |
| `Device.kind` | `earbuds`（新增，见 `schemas.DEVICE_KINDS`） |
| `Device.runtime_package` | `iflybuds-host-collector/<版本>`（不是 Android 包名，是 collector 标识） |
| `Device.control_transport` | `inbox` |
| `meta.device_kind` | `IFLYBUDS_AIR2` |
| `meta.device_adapter` | `iflybuds-host-collector/0.1.0` |

`kind` 不是能力声明。后端不知道 `earbuds` 没有摄像头，也不该知道——控制台照样能对它
下发 `CAPTURE_PHOTO`，由采集器回一条带原因的 `REJECTED`。这与 adb connector 里
`UNSUPPORTED_REASON` 表的处理方式一致：能力边界由设备侧回答，不由后端猜。

## 3. 音频输入（上行）

```text
CAPTURE_AUDIO 请求 → 本地策略 → ffmpeg 录一段 WAV → 本地 spool → Ingest API
                                                        ↑ 断网时留在这里
```

- **格式**：16k 单声道 WAV。耳机麦克风走 HFP，链路本身就是这个规格；再往上采样只是
  把带宽浪费在插值上，而 16k 单声道恰好是 ASR sidecar 最省事的输入。
- **契约**：`modality=audio` 的标准 `SourceEnvelopeIn`，附件为 WAV。设备差异只出现在
  `meta.device_kind / device_adapter`，记忆平台内部不认识 IFLYBUDS。
- **幂等键**：`<会话 id>-<序号>`，会话 id 一次进程生命周期一个。
- **离线**：录音与上传分离。录必须在请求到达的那一刻就地完成（麦克风就那一瞬间可用），
  传可以等网络恢复。断网期间录的音留在 spool，恢复后按落盘顺序补传。
- **电平进回执**：每条 `EXECUTED` 带 `peak_level`。「录到了但一片静音」是这条链路最常见
  的失败（耳机麦克风没被系统选中），不上报电平的话要等转写返回空文本才发现。

### 3.1 本地采集预算

`max_duration_seconds`（默认 60）是**设备侧**的上限。云端请求 300 秒时按 60 秒执行，
并在回执里同时给出 `requested_duration_seconds=300` 与 `effective_duration_seconds=60`。
不静默执行原始时长，也不直接拒绝——控制台的诉求是「录一段」，但它必须知道自己要的
300 秒没有生效。

## 4. 音频推送（下行）

```text
REMINDER_SIGNAL(allow_tts=true) → inbox/WS → 播放前核对输出设备 → say 播报 → 回执
```

复用现成的提醒消息，没有新增消息类型。设备侧的处理：

| 情况 | 回执 |
| --- | --- |
| 播报成功 | `PRESENTED` → `SPOKEN` → `DISMISSED` |
| `allow_tts=false` | `REJECTED`（未授权语音播报） |
| 默认输出设备不是耳机 | `REJECTED`（附实际设备名） |
| 播放命令失败 | `FAILED` |

两个刻意的决定：

**播完即终结（DISMISSED）。** 耳机上没有「用户点掉提醒」这个动作，播放结束就是这条
消息在设备侧的终局。不落终态的话它会一直留在待投递集合里，每次重连都再推一遍。

**输出设备核对是硬策略。** macOS 的 `afplay` 不能指定输出设备，`say -a` 可以，但都无法
替用户切换系统默认输出。所以播放前核对默认输出设备是不是耳机，不是就拒播。这是
04 号文档「策略在边缘执行」在输出方向上的对应物——云端不可能知道那台机器当前的默认
输出设备是什么，而把一条私人提醒从笔记本外放出去，比漏掉它严重得多。

`REJECTED` 原本是 `CAPTURE_REQUEST` 的专用终态（见 `schemas.DELIVERY_RECEIPT_STATUSES`
的注释），这里把它用在了提醒上。理由是它要区分的正是「策略正常拒绝」与「投递失败」，
拒播落在同一个区分上；用 `FAILED` 会让控制台以为链路坏了，用 `DISMISSED` 会让它以为
用户听到了。

### 4.1 音色必须按正文语言选

真机第一次播报出来的是**一串听不懂的英文音节**：`say` 用系统默认音色（英文）念中文，
返回码 0，回执照样是 `SPOKEN`。也就是说这个故障在云端完全不可见。

所以采集器自己负责选音色：正文含 CJK 就挑一个 `zh_*` 音色（优先 Tingting），非中文正文
保持系统默认。实际用了哪个音色写进 `SPOKEN` 回执的 `voice` 字段——「说出来了」和
「说的是人话」是两件事，只有后者能被听懂，而回执必须让人能追到这一步。

一台中文音色都没有的机器上仍然会播（宁可乱码也不静默丢提醒），但 `voice` 会是
`system_default`，`collector devices` 也会提前警告。

## 4.2 语音闭环：从「说了一句话」到「耳机里响一句」

前面四节讲的是通道。通道打通之后，真正的应用是这条闭环：

```text
说话 → VAD 分段 → 上传 → ASR 转写 ─┬─ 命中唤醒词 → 查记忆 → 答案念回耳朵（voice_qa）
                                    │
                                    └─ 普通陈述 → 事实抽取 → 候选门 → 事件 → 投影
                                                                          ↓
                                              耳机播报 ← 措辞 ← 打扰预算 ← 规则信号
                                                        （voice_delivery）
```

四个环节各自的边界：

| 环节 | 位置 | 谁决定 |
| --- | --- | --- |
| 什么时候录 | 设备侧 VAD（`collector/vad.py`） | 有没有人在说话 |
| 录到的算不算事实 | 现有候选门 | 规则 + 置信度，不是模型说了算 |
| 什么时候开口 | `signals/rules.py` + `voice_delivery` 打扰预算 | **确定性规则** |
| 怎么说那句话 | `voice_delivery/wording.py` | LLM（且仅此一处） |

「什么时候开口」与「怎么说」的分离不是洁癖，是 `MemorySignal` 模型注释里写死的契约：
*生成走规则引擎，措辞归 Agent；平台绝不用 LLM 生成信号*。把这两件事合并，系统就退化成
「模型觉得该说话就说话」——那是另一个产品，要改契约才能做。

### 4.2.1 会话制

默认不监听。必须显式开启一段记忆会话（`collector listen`，或云端下发
`START_PERIODIC`），`STOP` 即停。**隐私暂停期间麦克风保持关闭**，不是「采了不传」——
耳机没有佩戴检测，暂停开关是用户唯一能真正关掉麦克风的手段。

### 4.2.2 唤醒词为什么在云端识别

真正的离线唤醒词需要额外的模型与原生依赖，与这个采集器「扔到任意一台机器上都能跑」的
前提冲突。所以唤醒词在**转写之后**识别：代价是它只在会话进行时有效（设备得先听见才有
转写）——这与会话制的隐私默认恰好一致，没开会话时它本来就不该听见任何东西。

唤醒词只认句首：「我跟小忆说过这事」是陈述不是呼叫。命中唤醒词的转写**不进事实抽取**，
否则记忆里会攒出一堆「用户其实是在提问」的句子。

### 4.2.3 回答问题不走打扰预算

安静时段、每小时上限管的是「系统主动开口」。用户自己问的问题当然要答——半夜问一句
却被静音策略吞掉，那是 bug 不是克制。答案的 TTL 也比主动提醒短得多（120s vs 300s）：
问完十几秒才响的答案已经没用了。

## 5. 至少一次投递怎么处理

下行是至少一次的（长连补投 + inbox 轮询会让同一条请求到达两次），而采集和播报都有
副作用。采集器的做法是**先占坑再执行**，占坑记录落盘：

| 重投时的状态 | 行为 |
| --- | --- |
| 没见过 | 正常执行 |
| 见过且有终态 | 不重新执行，原样补发上次的终态（`duplicate_delivery=true`） |
| 见过但没有终态 | 回 `FAILED`，原因 `collector_restarted_mid_flight` |

第三种是采集器在处理途中被杀掉的情况。既不能宣称执行成功，也不能装作没发生过——
如实告诉控制台这条请求结局未知，且没有被重复执行。

## 6. 支持的动作

| 动作 | 耳机运行时 | 说明 |
| --- | --- | --- |
| `CAPTURE_AUDIO` | ✅ | 录一段定长音频并上传 |
| `START_PERIODIC` | ✅ | 宿主侧周期采集，每轮录一段短音频 |
| `PAUSE` / `RESUME` | ✅ | 隐私暂停；暂停期间麦克风不会被打开 |
| `STOP` | ✅ | 结束周期采集会话 |
| `CAPTURE_PHOTO` | ❌ | 耳机没有摄像头，回 `REJECTED` |

`PAUSE` / `RESUME` / `STOP` 在暂停期间也必须可执行——否则一旦暂停就再也没法通过云端
恢复。

## 7. 已验证与未验证

**已验证（2026-07-25，真耳机 + 真实后端 + 真 ASR sidecar）：**

- 设备注册按 name 幂等，`kind=earbuds` 通过校验、拼错的 kind 被 422 拒绝。
- 按名字解析输入设备：耳机连上后索引变成 `[1]`（此前那批设备是另一套序号），
  匹配照样命中——这是不缓存设备索引的直接证据。
- 实录：3.00s / 96078 字节、8s 请求实录 7.98s，峰值电平 0.10–0.15，格式确为 16k 单声道。
- `CAPTURE_AUDIO` 全链路：inbox 排队 → 采集器录音上传 → `EXECUTED`（带电平、实际时长、
  信封 id）→ 消息 `CLOSED`，且后端不替设备写终态。
- `CAPTURE_PHOTO` 被设备侧拒绝：`REJECTED`「IFLYBUDS 是耳机，没有摄像头」。
- 语音推送两种结局都验过：默认输出是笔记本扬声器时 `REJECTED`（**没有外放**）；
  耳机为默认输出时 `RECEIVED → PRESENTED → SPOKEN → DISMISSED`，回执带
  `voice: Tingting` 与 `output_device: iFLYBUDS Air 2`。
- 播报途中被 Ctrl-C 打断的消息，在下次运行时按「重启前未完成」回 `FAILED`，
  不会被重复播报。
- Ingest 幂等：同幂等键重投返回既有信封。

**未验证：**

- 连续采集下 SCO 链路对耳机与主机续航的影响。
- 采集过程中耳机断连重连的恢复行为（代码每次录音前重新解析设备，未真机断连过）。
- **ASR 转写尚未拿到非空结果**：sidecar（faster-whisper small）正常响应，但两段录音都
  返回 `segments: []`。把落盘 WAV 直接喂给 sidecar 复核，结果一致——说明是音频里没有
  可识别人声（录制时无人说话），不是管线问题。需要一次「录音时确实在说话」的验收。

## 8. 已知限制

1. **宿主机必须在场。** 这是这条路线的根本代价。耳机连在手机上时，这个采集器帮不上忙，
   除非把它移植成手机 App 的一部分。
2. **只实现了 macOS。** 录音走 avfoundation、播报走 `say`。Linux/Windows 会在解析设备时
   明确报错，而不是假装能录。
3. **拿不到佩戴状态。** 第三方读不到入耳检测，「摘下即停止采集」在耳机这一侧无法实现，
   隐私开关只能由宿主侧承担（`PAUSE` / `PRIVACY_PAUSE` / 启动时暂停）。
4. **不经过讯飞自己的录音与转写。** 这条链路只把耳机当麦克风和扬声器用，不碰厂商 App，
   也不依赖它的云端转写。如果要用讯飞的转写结果，那是另一条路线（导出文件再导入），
   07 号文档已经把人工导出排除在产品链路之外。
5. **鉴权沿用 `/internal/v1` 现状**（本机/内网可信域）。任何能访问该端口的人都能让这台
   机器录音——与眼镜的采集控制面是同一个待办，见 04 §5.2。

## 8.1 语音闭环的已知缺口

1. **纯时间条件的规则不会自己到点触发。** `evaluate_signals_for_entity` 只在
   `projection.recompute` 时被调用，所以「说过要做某事、三小时还没做」这类规则不会
   自己响——除非那个实体恰好因为别的原因被重算。现有的 `STALE_LOCATION` 已经有这个
   问题。要做「主动建议」必须先补一个周期性的规则评估器。
2. **情绪价值没有落地。** 它卡在契约上而不是实现上：现有约束下「什么时候开口」必须是
   确定性规则，而情绪回应的触发条件（"他听起来很累"）天然是模型判断。要做就得先决定
   是新增一类明确的规则信号（如检测到特定情绪词 → `EMOTION_MOMENT`，仍是规则），
   还是修改契约允许模型发起。前者可控，后者是产品方向的改变。
3. **VAD 是能量判据。** 嘈杂环境会误触发，代价是多传几段空音频（云端转写为空后被
   `empty_transcript` 丢掉，不会产生错误记忆）。真要在户外用，需要换 Silero/WebRTC 一类
   的模型 VAD。
4. **多设备时「该对谁说」未定义。** 当前实现取家庭里第一副耳机。
